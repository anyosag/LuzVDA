**Note on `displays.csv`: invalid.** The display sampler from P4 recorded only the PC's two physical monitors at their idle positions (`\\.\DISPLAY2` 2560x1440 primary, `\\.\DISPLAY1` 1920x1080) in all 231 samples, including during every stream. It never saw `\\.\DISPLAY75`, which Apollo created and streamed from.
- The likely cause is that `System.Windows.Forms.Screen.AllScreens` caches the screen list for the life of a process. In a loop with no message pump it's never refreshed, so the sampler kept repeating its first reading.
- The single-display result above therefore rests on Apollo's display_device log alone. Stream screenshots can't show whether the PC's own monitors are active.
- **For the next test,** sample in a fresh process each time, or use `EnumDisplayMonitors` or `QueryDisplayConfig`.

## Surprises
1. **Resumes still cost 2 HDR switches** when HDR stays on (R1, R2, R3, R5, R6). It all happens before `New streaming session started`, so it isn't visible on the Mac, but it's still the main fail in the pass table.
2. **R4 (HDR off) left the display in HDR:** 0 HDR switches, then `Client dynamicRange: 0, Display is HDR: true`. Apollo streamed SDR from an HDR desktop, and the Mac reported a normal SDR picture.
   - This passes the "at most 1" rule, but the behavior changed: in the stream test the display went to SDR.
   - Decide whether that's intended. It avoids an HDR switch, but the PC desktop renders in HDR for an SDR client.
3. **The display sampler was stale for the whole run** (see the note under the pass table). Use a different method next time.
4. **Untested:** reapplying "only this display" after a re-creation (R4 → R5 in the stream test). No resume re-created the display this time, so the isolation fix wasn't exercised.
