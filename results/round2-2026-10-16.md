## Notes per test

### S: smoke-test trace
Decoded with `tracerpt` (TraceLogging, event names as task names):
- `DriverStarted` ×2 (the device restart);
- `DisplayAdded`, then `SwapChainAssigned`;
- immediately `SwapChainUnassigned` + **`SwapChainEnded Result=0x887A0026`** (DXGI_ERROR_ACCESS_LOST), with `SwapChainAssigned` again 156 ms later;
- at removal: `SwapChainUnassigned`, `SwapChainEnded 0x0`, `DisplayRemoved 0x0`.

### L1
- At launch Apollo applied EnsureOnlyDisplay. Available devices: Optix G24C = inactive, Odyssey G5 = inactive, MacBook = active (primary).
- In the first 3.6 s (22:49:10.7–22:49:13.8, while Windows set the mode and turned HDR on), the swap chain was assigned and lost (`0x887A0026`) **6 times**. Then it stayed assigned for the rest of the 75 s.
- No capture restarts.

### R4: re-creation when the Mac's description changes
- The Mac set `fork.hdrPeakOverride = 1000`. LuzLunar sent `luzHdr=1000,1000,0`, and its Describing line said `HDR 1000/1000 nits`.
- **The black level went from 50 (0.005 nits) to 0** with the override, and Apollo created the display with `black 0 nits`. This looks like a LuzLunar quirk: the override replaces the black level too.
- Apollo: `the client streams to another screen, re-creating \\.\DISPLAY115`, `added … in 0 ms`, then `resume handled in 1822 ms, 0 mode changes, 2 HDR switches`. The stream opened at 22:52:41.43, about 4.9 s after the request; the Mac saw the picture at +6 s.
- **A brief second display during the re-creation:** at 22:52:36.946 the sampler saw `\\.\DISPLAY115 primary` plus `\\.\DISPLAY1 1920x1080@3024,0`, the Optix G24C, which Windows turned back on.
  - Apollo reapplied EnsureOnlyDisplay at 22:52:37.849, and every later sample shows one display.
  - This is the stream test's lost-isolation problem, now fixed: it lasted under 1 s and was corrected before the stream opened.
  - Apollo's device list at that moment named only `MacBook = active (primary), Optix G24C = inactive`; the Odyssey G5 was missing from the list.
  - The reapplied configuration had `"device_id": ""`. At launch it was the display's id.
- **A capture restart:** 22:52:46.352, `Capture restarts: the desktop duplication was lost [0x887A0026]`, about 5 s into the stream. **There was no swap-chain event within 2 s** (the last was `SwapChainAssigned` at 22:52:40.586), so the driver's swap chain didn't cause it. The Mac reported no visible effect.

## Surprises
1. **The HDR fix works.** A resume that keeps HDR costs 0 switches, and a resume to SDR turns HDR off.
2. **Re-creation now restores isolation, after a brief blip.** For under 1 s, Windows turned one PC monitor back on (at 3024,0) until Apollo reapplied EnsureOnlyDisplay. Windows didn't move.
3. **Swap-chain churn while HDR or the mode changes:** repeated assign / `ACCESS_LOST` cycles, 6 at L1's launch and 2 per HDR switch. That's harmless so far, but it's the same error code as the capture restart.
4. **R4's capture restart has no driver-side cause.** No swap-chain event came within 2 s. The next thing to look at is what Windows or DWM did at 22:52:46.
5. **LuzLunar's HDR peak override also sets the black level to 0,** so Apollo builds an EDID with `black 0 nits`.
6. **R4's re-applied config has an empty `device_id`,** and its device list left out the Odyssey G5.
